# 근거 카드 작성

카드는 근거 한 조각을 적은 파일 한 개다. **근거 하나 = 카드 한 장.**
한 파일에 몰아쓰지 않는다.

카드를 쓰는 사람 중에는 Git도 Markdown도 모르는 사람이 있다.
**쉬운 한국어로 말하고, 사람이 할 일은 최소로 만든다.**

---

## 1. 먼저 두 가지를 확인한다

물어보지 않고 시작하지 마라. 종류마다 필요한 항목이 다르다.

**① 어떤 종류인가**

| 종류 | 무엇 | 폴더 |
|---|---|---|
| `O` | 내가 직접 써보고 느낀 관찰 | `01_evidence/team/` |
| `E` | 외부 자료 (보고서·논문·기사) | `01_evidence/desk/` |
| `S` | SuperSOL 화면 분석 | `01_evidence/screen/` |
| `C` | 경쟁 앱 분석 | `01_evidence/competitor/` |

**② 누가 쓰는가** — 팀장 / 팀원1 / 팀원2 / 팀원3
번호 대역이 사람마다 다르기 때문이다. 대화에서 알 수 없으면 묻는다.

## 2. 번호는 직접 세지 않는다

```
python3 scripts/next_id.py <종류> <이름>
```

예: `python3 scripts/next_id.py O 팀원3` → `O-401`

사람에게 "몇 번으로 할까요?"라고 묻지 마라. 이 스크립트가 자기 대역의 마지막
번호를 찾아 +1 해준다. 대역이 사람마다 분리돼 있어 4명이 동시에 만들어도 겹치지 않는다.

## 3. 카드를 쓴다

### 모든 카드 공통 (5개)

```yaml
id: O-401
type: team          # team / desk / screen / competitor
author: 팀원3
date: 2026-08-05
summary: 한 줄 요약   # 필수. 카드가 수백 장 됐을 때 이것만 모아 본다
```

`summary`를 빠뜨리지 마라. 한 줄로, 카드를 안 열어도 무슨 내용인지 알게 쓴다.

### O 카드 — 추가 항목 없음

가장 단순하다. 위 5개면 끝이다. **8/7 오전 마감이라 여기서 막히면 안 된다.**

```markdown
---
id: O-401
type: team
author: 팀원3
date: 2026-08-05
summary: 내 보험 현황을 찾는 데 스크롤이 두 번 필요했다
---

## 사실 (내가 실제로 본 것)
보험 Tab을 열었을 때 첫 화면에 카드가 6개 보였다.
내 보험 현황은 스크롤을 2번 내린 뒤에 나왔다. 위쪽 3개는 상품 광고였다.

## 내 해석 (내 생각)
내 보험 상태를 먼저 보고 싶은 사용자에게는 순서가 어긋나 있을 가능성이 있다.
```

### E 카드 — 출처 4요소가 없으면 카드를 만들지 않는다

추가: `source_org`(발행기관) · `published`(발행일) · `url` 또는 `local_file` ·
`page`(인용 페이지) · `grade`(근거 등급)

넷 중 하나라도 없으면 **카드를 만들지 말고** `_meta/source_wishlist.md`에 적는다.
요약 기사는 근거로 쓰지 않는다. 원본 보고서를 찾는다.

### S 카드 — 추가: `screen` (캡처 파일 경로)

### C 카드 — 추가: `app` · `user_task` · `grade` · `capture`

근거 등급을 반드시 붙인다. **D등급(확인 안 됨)은 카드를 만들지 않는다.**

| 등급 | 뜻 |
|---|---|
| A | 우리가 직접 찍은 화면 |
| B | 공식 문서·공지·앱스토어 설명 |
| C | 언론 기사·앱 리뷰 (보조 근거로만) |
| D | 확인 안 됨 → 카드 만들지 않음 |

## 4. 본문은 반드시 두 칸으로 나눈다 — 가장 중요하다

| 종류 | 첫 칸 | 둘째 칸 |
|---|---|---|
| O | `## 사실 (내가 실제로 본 것)` | `## 내 해석 (내 생각)` |
| E | `## 사실 (자료에 적힌 그대로)` | `## 내 해석 (내 생각)` |
| S | `## 화면에서 확인되는 사실` | `## UX 관점 해석 (아직 문제 아님)` |
| C | `## 화면에서 확인되는 사실` | `## 비교 관점 해석 (아직 문제 아님)` |

**첫 칸에는 반박할 수 없는 것만 쓴다.** 카드 개수, 탭 수, 화면에
적힌 문구 그대로, 자료에 적힌 숫자 그대로.

### 첫 칸은 짧게 쓰지 않는다 — 카드가 3층인 이유

| 층 | 누가 읽나 | 길이 |
|---|---|---|
| `summary` 한 줄 | 카드가 수백 장 됐을 때 훑는 용도 | **짧게** |
| 첫 칸 (사실) | **사람이 판단할 때** | **자세히** |
| 원본 (PDF·캡처) | 최종 확인이 필요할 때만 | — |

**짧게 요약하는 것은 `summary`의 일이다.** 첫 칸까지 요약해버리면 사람이 판단할 때
원본을 다시 열어야 하고, 그러면 카드를 만든 의미가 없다.

- **숫자는 원문 그대로.** `61%`를 "약 60%"로, `1,200명`을 "1천여 명"으로 바꾸지 않는다
- **화면·자료에 적힌 글자는 그대로 옮긴다.** 다듬으면 나중에 검색이 안 된다
- **이 카드가 다루는 것과 관련된 내용은 빠뜨리지 않는다.**
  같은 쪽·같은 화면에 관련된 것이 셋이면 셋 다 적는다

**단, 관련 없는 것까지 옮기지 않는다.** 근거 하나 = 카드 한 장이므로
그 근거에 필요한 범위까지다.

**분량을 세지 마라.** 줄 수를 채우려고 같은 말을 늘려 쓰면 밀도가 떨어져서
오히려 안 읽힌다. 다만 첫 칸이 2~3줄로 끝났다면 빠뜨린 게 없는지 원본을 다시 보라.

종류별 상세 기준은 각 도우미 안에 있다
(`.claude/agents/desk-researcher.md` · `screen-analyst.md` · `competitor-analyst.md`).

**둘째 칸에만 생각을 쓴다.** 그리고 반드시 이렇게 쓴다.

> "~할 가능성이 있다" / "~로 보인다"

이렇게 쓰지 않는다.

> ❌ "사용자는 ~를 불편해한다" / "~가 문제다" / "명백히" / "확실히"

**왜 이렇게까지 하는가:** 아직 사용자에게 물어보지 않았기 때문이다. 우리가 문제라고
생각한 것과 사용자가 불편해하는 것은 다를 수 있다. 이 두 칸의 구분이 무너지면
나중에 "그거 근거가 뭐예요?"라는 질문에 답할 수 없다.

AI가 쓴 문장이 단정형이면 **네가 고쳐라.** 사람에게 넘기기 전에.

## 5. 다 쓴 뒤

```
python3 scripts/build_index.py
```

목록을 다시 만든다. 그리고 사람에게 만든 카드 ID와 파일 경로를 보여준다.

**커밋은 하지 않는다.** "`/save` 치시면 올라갑니다"라고 안내한다.

---

## 하지 않는 것

- 근거 없이 카드를 만들지 않는다. 없으면 `_meta/source_wishlist.md`에 적는다
- 남의 대역 번호를 쓰지 않는다
- 한 카드에 근거를 여러 개 몰아넣지 않는다
- 카드를 지우지 않는다. 틀렸으면 내용을 고치거나 `status`만 바꾼다
