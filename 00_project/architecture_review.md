## 1. 진단 요약

SETUP.md 초안에서 문제 19개를 발견했다. 이 19개는 서로 독립적이지 않고 **뿌리 5개**에서 파생된다. 뿌리를 고치면 19개가 함께 해결된다.

유지할 설계는 다음 4개다. 그대로 간다.

- **index.csv를 소스가 아닌 생성물로 처리** — 폴더 소유권으로 충돌을 없앤 뒤 남는 유일한 공유 쓰기 지점을 정확히 제거했다.
- **agent별 쓰기 경로 제한** — 추적성을 사람의 성실함이 아니라 권한으로 지키는 유일한 장치.
- **red-team-auditor를 `_meta/` 전용으로 분리** — 생성과 검사의 분리. 점검 8번(rejected 0건 경고)은 프로젝트 핵심 원칙을 기계 검사로 번역한 항목이다.
- **main 단일 브랜치 + 커밋 메시지가 곧 워크로그** — 비개발자 1명 기준에서 배울 개념 수를 최소화한 올바른 절충.

## 2. 뿌리 5개와 해결 구조

### ① 상태 전이를 강제하는 주체가 없다 (문제 1, 2, 7, 13)

H→P, SOL→M 승격 지점에 문지기가 없어 폴더가 게이트인 척만 한다. M은 아예 폴더·필드·검사·agent가 전부 없어 추적성이 SOL에서 끊긴다.

**해결: 카드 생성 권한을 커맨드에 몰아준다.**
- `/gate1`이 P 카드를 만드는 유일한 경로, `/gate2`가 M 카드를 만드는 유일한 경로
- 그 외 경로로 생성된 P·M 파일은 검사에서 ERROR
- M 카드 폴더를 `04_painpoint`와 대칭 위치에 신설
- Gate 1 "미판정 H 0건"을 기계 검사 항목으로 추가
- **H도 같은 대칭을 적용한다.** `synthesizer`는 `02_hypothesis/draft/`에만 쓰고,
  8/17 종합 회의에서 확정된 것만 `02_hypothesis/`로 승격된다.
  draft→H→P→M이 전부 "회의에서만 승격"이라는 하나의 규칙으로 통일된다.

### ② 소유권 단위를 폴더로 잘못 잡았다 (문제 8, 책임 중복 일부)

실제로 충돌을 막는 건 ID 대역(x1xx~x4xx)인데 문서는 폴더라고 썼다. `01_evidence/team/`은 W0에 4명 전원이, `desk/`는 3명이 쓰므로 **첫 주에 규칙이 깨진다.**

**해결: "자기 대역 번호의 파일만 만들고 고친다"로 재정의.**
- 폴더는 분류일 뿐 소유물이 아니다
- O 카드 전원 작성, desk 공동 작업, SOL 공동 작성이 모두 규칙 위반이 아니게 된다
- `traceability_check` #9(대역 위반)가 이 규칙의 자동 감시자가 된다.
  단 H·P·M은 대역이 없으므로 #9 검사 대상에서 제외한다 — CLAUDE.md에 명시
- 부수 교정: 기존 §5의 `S-1xx`/`C-2xx`/`C-3xx`는 CLAUDE.md 대역 규칙과
  어긋나 있었다. 번호가 소유 단위가 되면 S·C 카드 전부가 대역 위반으로 잡히므로
  같은 커밋에서 200/300/400번대로 바로잡았다
- `PROJECT_PLAN.md` §5와 `CLAUDE.md`를 **동시에** 수정해야 한다

### ③ 검사가 필드의 존재만 보고 내용·생성경로를 안 본다 (문제 2, 9, 12, 13)

`validated_by`가 비어 있지만 않으면 통과하고, 파일명이 `연락처`가 아니면 개인정보가 통과한다. `build_index.py`가 참조하는 `summary` 필드는 카드 필수 필드 목록에 존재하지 않는다.

**해결: 화이트리스트 + 스키마 검사로 뒤집는다.**
- 개인정보: `03_validation/`·`07_usertest/` 하위는 `design/`·`anonymized/`·`analysis/`만 커밋 허용, 나머지 전부 차단
- P 카드는 `survey_q` + `n` + `rate` 값의 형식까지 검사
- 모든 카드에 1줄 `summary` 필수화 → index 컬럼 불일치와 종합 단계 Context 문제가 동시에 해결된다

### ④ 같은 규칙이 4곳에 복제돼 있다 (책임 중복 5개, 문제 5, 11, 14)

금지 표현·근거 등급·source_types가 각각 4곳에 있고, 존재하지 않는 문서(`project_flow.md`)를 참조하는 곳도 있다.

**해결: 단일 출처 원칙.**
- 상수·불변 규칙 → `CLAUDE.md` (항상 로드)
- 작업 절차 → Skill
- 위반 검출 → `traceability_check.py`
- 판단형 검사(유도질문, rejected 0건) → `red-team-auditor`만
- 나머지는 전부 참조만. 커밋 메시지 규칙은 SETUP에서 `/save` 안으로 이동
- `/audit`을 성격별로 분리 (추적성 검사 ≠ 설문 문항 감사)

### ⑤ 세팅 범위가 일정에 안 맞는다 (문제 5, 10)

3일에 산출물 21개는 불가능하다. SETUP 1절이 "1~4까지만 되면 합류 가능"이라 옳게 판단해 놓고 9절 체크리스트가 이를 어겼다.

**해결: 7주간 실제 호출 횟수로 가지치기.**
- `/evidence`(얇은 래퍼) 제거, `deliverable-format` Skill → 템플릿 파일로 강등
- Skill·agent를 "처음 필요해지는 날짜"에 맞춰 분산 배치 (5절 표)

## 3. 확정된 결정

**결정 1 — `git checkout -- *` 차단 해제**
deny 목록에서 제거한다. `push --force`/`reset --hard`는 남의 작업을 날리지만 이것은 자기 작업만 되돌리는 복구 도구다. 막아두면 사소한 실수마다 팀장이 호출된다. 나머지 6개(`push --force`, `push -f`, `reset --hard`, `rebase -i`, `clean -fd`, `rm -rf`)는 유지한다.

**결정 2 — 8/7 오후 리서치 개시에 맞춘 단계적 세팅**
agent 7개를 전부 W1로 미루려던 계획을 수정한다. 리서치 3종만 8/7 오전으로 당기고 나머지 4개는 날짜별로 분산한다. (5절 표)

**결정 3 — 소유권 재정의를 킥오프 전에 완료**
`PROJECT_PLAN.md` §5와 `CLAUDE.md`를 8/5 킥오프 전에 함께 수정해 한 가지 버전만 존재하게 한다. 첫 주에 두 버전이 돌면 그 규칙은 끝까지 신뢰받지 못한다.

## 5. 8/7 오후 개시로 생긴 리스크 2개

**① O 카드 마감이 8/7 오전으로 당겨진다 — 세팅보다 급하다**

PROJECT_PLAN은 O 카드에 조건을 붙였다. "AI 분석을 보기 전에 먼저 하세요. AI가 뭐라고 했는지 보고 나면 자기 생각이 오염됩니다."

8/7 오후에 AI 리서치가 돌면 그 뒤에 쓴 O 카드는 오염된 카드다. W0 전체(8/5~8/9)에 여유 있게 잡혀 있던 일이 **킥오프~8/7 오전, 실질 이틀**로 줄어든다. 4명 전원이 해야 한다.

→ 킥오프에서 "O 카드는 8/7 오전까지"를 명시적으로 못박는다.

**② 앞당겨진 3일은 버퍼지 수집량이 아니다**

수집이 8/10이 아니라 8/7에 시작되면 3일이 생기지만 **8/16 마감은 그대로 둔다.** PROJECT_PLAN이 미리 경고한 지점이 정확히 여기다 — "여기서 '조금만 더 찾아보자'가 시작되면 8/21 배포가 깨집니다."

번 3일은 8/17 종합을 앞당기거나, 리스크 완화책인 "종합 도우미 미리 한 번 돌려보기"에 쓴다. 수집 기간을 늘리는 데 쓰면 이득이 전부 사라진다.

## 6. 잔여 리스크 (구조로 완전히 제거 불가)

**Skill은 호출이 보장되지 않는다.** 팀원3이 "카드 만들어줘"라고 치면 `evidence-card` Skill이 안 불릴 수 있고, 포맷이 틀린 카드가 조용히 생긴다.

완화책은 있다 — 절대 규칙은 항상 로드되는 `CLAUDE.md`에 두고, 중요한 절차는 Skill이 아니라 커맨드로 감싸고, 틀린 카드는 `/audit`이 사후에 잡는다. 하지만 "반드시 불린다"는 보장은 만들 수 없다. 알고 감수하는 리스크로 남긴다.

SETUP.md 마지막 줄("Research Rule을 Skill에 넣으면 로드 안 될 때 규칙이 무시됩니다")이 이 위험을 이미 정확히 인지하고 있고, 그 판단은 옳다.
