## 0. 한 장 요약

우리는 SuperSOL 보험 Tab을 더 예쁘게 다시 디자인하는 것이 목표가 아닙니다.

**"우리가 문제라고 생각한 것"이 진짜 사용자의 문제인지 먼저 확인하고, 확인된 것만 고치고, 고친 것이 실제로 나아졌는지 다시 확인하는 것**이 목표입니다.

그래서 우리 프로젝트는 사용자에게 두 번 물어봅니다.

1. **1차 (8월 중순, 설문)** — "이게 정말 불편하신가요?"
2. **2차 (9월 중순, 사용자 테스트)** — "우리가 만든 게 정말 나아졌나요?"

이 두 번의 조사 사이에 모든 작업이 배치되어 있습니다. 그래서 **조사 일정(8/15 오후 배포 ~ 8/19 마감 · 9/11 테스트 시작)만 고정이고**, 나머지 날짜는 그 둘에 맞춰 조절합니다.

AI(Claude)는 자료를 빠르게 모으고 정리하는 역할을 합니다. **무엇이 문제이고 무엇을 고칠지 결정하는 것은 사람입니다.**

## 1. 목표와 핵심 원칙

### 최종 목표

> 리서치로 문제 가능성을 찾고 → 실제 사용자에게 진짜 문제인지 검증하고 → 검증된 문제만 개선하고 → 개선안을 다시 사용자에게 테스트해서 얼마나 좋아졌는지 숫자와 말로 보여준다.

### 이 프로젝트를 지배하는 하나의 원칙

**우리 팀이나 AI가 "이거 불편하겠는데?"라고 생각한 것과, 실제 사용자가 불편하다고 느끼는 것은 다를 수 있습니다.**

이게 이 프로젝트의 전부입니다. 앞으로 나오는 모든 규칙은 이 원칙 하나에서 나옵니다.

그래서 우리는 이렇게 합니다.

- 우리가 발견한 문제를 처음부터 "문제"라고 부르지 않습니다. **"문제일 것 같은 것"(문제 가설)**이라고 부릅니다.
- 사용자에게 물어봐서 확인된 것만 **"진짜 문제"(검증된 Pain Point)**로 승격시킵니다.
- 개선은 승격된 것만 대상으로 합니다.

### 발표에서 우리가 하고 싶은 말

❌ "이 화면이 불편해 보여서 이렇게 바꿨습니다."

⭕ "리서치로 7개의 문제 가설을 세웠고, 83명에게 물어본 결과 4개가 확인되고 3개는 아니었습니다. 확인된 4개를 개선했고, 8명에게 다시 테스트해서 이만큼 좋아졌습니다."

## 2. 우리 팀 용어집

문서 전체에서 이 6개 단어만 씁니다. 회의에서도 이 단어로 말합니다.

| 용어 | 뜻 | 예시 |
|---|---|---|
| **근거 (Evidence)** | 우리가 모은 사실 자료 한 조각 | "20대의 보험 이해도가 낮다는 보험연구원 2025 보고서 12쪽" |
| **카드** | 근거 한 조각을 적어둔 파일 한 개. 우리는 자료를 문서 하나에 몰아쓰지 않고 카드 여러 장으로 쪼개서 관리합니다 | `E-101.md` 파일 하나 |
| **ID** | 카드마다 붙는 고유 번호. 나중에 "이 주장의 근거가 뭐였지?"를 되짚기 위한 것 | `E-101`, `S-204`, `H-003` |
| **문제 가설** | 문제일 것 같지만 아직 사용자에게 확인 안 된 것 | `H-003` |
| **검증된 Pain Point** | 사용자 조사로 진짜 문제라고 확인된 것 | `P-001` |
| **게이트 (Gate)** | 다음 단계로 넘어가도 되는지 팀이 다 같이 확인하는 관문. 통과 못 하면 진행하지 않습니다 | Gate 1 (8/25 회의) |

### ID 종류

| ID | 무엇 | 누가 만드나 |
|---|---|---|
| `O-###` | 우리 팀원이 직접 써보고 느낀 관찰 | 팀원 전원 |
| `E-###` | 외부 자료 조사 결과 (보고서, 논문, 기사) | 팀원 전원 + AI |
| `S-###` | SuperSOL 화면 분석 결과 | 팀원1 + AI |
| `C-###` | 경쟁 앱 분석 결과 | 팀원 전원 + AI |
| `X-###` | 멘토님께 확인받은 답 | 팀원 전원 |
| `H-###` | 위 근거들을 종합한 **문제 가설** | 팀장 + AI |
| `P-###` | 설문으로 확인된 **진짜 문제** | 팀 전원 (Gate 1) |
| `SOL-###` | 개선안 | 팀장·팀원2 |
| `M-###` | 개선 효과 측정 결과 | 팀 전원 (Gate 2) |

## 3. 전체 흐름 한눈에

```
[1단계] 문제 찾기 — 8/5 ~ 8/14
   팀 관찰(O)   외부자료(E)   화면분석(S)   경쟁앱(C)
        └──────────┴──────────┴──────────┘
                        ↓
[2단계] 가설 세우기 — 8/13 초안 ~ 8/25 확정 회의
              문제 가설 (H)  ← 아직 확정 아님
                        ↓
        ┌── 설문조사 (8/15 오후 배포 ~ 8/19 마감) ──┐
        ↓                                       ↓
   확인됨 (Validated)                    아니었음 (Rejected)
        ↓                                       ↓
   진짜 문제 (P)                        기록으로 남김 → 발표에 포함
        ↓
[3단계] 개선하기 — 8/15 ~ 8/31
   와이어프레임(8/15~19) → 최종 UI 디자인(8/20~24) → React MVP(8/25~31)
        ↓
[4단계] 효과 확인 — 9/11 ~ 9/13
        ┌──── 사용자 테스트 (기존 앱 vs 우리 MVP) ────┐
                        ↓
              개선 효과 측정 (M)
                        ↓
[발표] 9/20
```

> ⚠️ **버전 2.0의 순서 주의 두 가지** — 일정이 앞당겨지면서 생긴 것이라 숨기지 않고 적어둡니다.
>
> 1. **설문(8/15)이 가설 확정 회의(8/25)보다 먼저 나갑니다.** 설문은 가설 **초안**
>    (H-001~H-008, status: draft) 기준으로 만들어졌습니다. 8/25 회의에서 가설을
>    확정하고, 설문 판정은 확정된 가설 기준으로만 합니다. 이 순서 뒤집힘은
>    `08_deliverable/limitations.md`에 기록합니다.
> 2. **와이어프레임(8/15~)과 최종 UI 디자인(8/20~24)이 Gate 1(8/25)보다 먼저입니다.**
>    그래서 Gate 1 전의 와이어프레임·디자인은 전부 **"가설 기반 시안"**입니다. SOL 카드
>    확정과 "개선안"이라는 이름은 Gate 1 이후에만 씁니다(연구 규칙 10). 8/25 회의에서
>    P로 확정되지 않은 가설의 화면은 시안에서 뺍니다 — 이미 그렸어도 뺍니다.
>    조사 결과가 항상 이깁니다(규칙 9).

**중요:** 위 그림에서 `H`(문제 가설)는 설문을 거치지 않고는 절대 `P`(진짜 문제)가 될 수 없습니다. 이건 규칙이 아니라 폴더 구조로 강제됩니다. AI가 만든 가설 초안은 `02_hypothesis/draft/`에, 팀이 확정한 `H` 카드는 `02_hypothesis/`에, `P` 카드는 `04_painpoint/` 폴더에 있습니다. 초안은 8/25 종합 회의를 통과해야 `H`가 되고, `H`는 Gate 1(같은 회의)을 통과해야 `P`가 됩니다. 각 승격은 회의에서만 일어납니다.

### 내 것과 남의 것을 가르는 기준은 폴더가 아니라 번호입니다

**규칙은 한 줄입니다. 내 번호 대역의 파일만 만들고 고칩니다.**

- ⭕ 내 번호로 새 카드 만들기 — **어느 폴더에서든 상관없습니다**
- ⭕ 내 번호 카드 고치기
- ❌ 남의 번호 카드 고치기 — 필요하면 그 사람에게 말합니다

폴더는 자료를 종류별로 정리해두는 서랍일 뿐, 누구의 소유물이 아닙니다. 위 표의 "주로 쓰는 폴더"는 "여기서 주로 일하게 될 것"이라는 안내지 출입 제한이 아닙니다.

그래서 아래는 전부 정상이고, 규칙 위반이 아닙니다.

| 하는 일 | 누가 | 어디에 |
|---|---|---|
| O 카드 (직접 써보고 느낀 것) | **전원 4명** | `01_evidence/team/` |
| 데스크 리서치 E 카드 | 팀장 · 팀원2 · 팀원3 | `01_evidence/desk/` |
| 개선안 SOL 카드 | 팀장 · 팀원2 | `05_solution/` |

네 명이 같은 폴더에 동시에 파일을 만들어도 번호가 겹치지 않으므로, 자료가 꼬이거나 덮어써지는 사고는 그대로 안 일어납니다.

**"내가 이걸 만들어도 되나?" 판단법 — 두 가지만 보면 됩니다.**

1. 내가 만들 파일 번호가 내 대역인가 → 그러면 만들어도 됩니다
2. 이미 있는 파일을 고치려는 건데 번호가 내 대역이 아닌가 → 그러면 손대지 않습니다

**예외 1 — 번호가 없는 공용 파일**
`_meta/decision_log.md`, `08_deliverable/outline.md`처럼 번호가 없는 파일이 몇 개 있습니다. 이것만 **다 같이 모였을 때** 수정합니다.

**예외 2 — H · P · M 카드는 대역이 없습니다**
회의에서만 만들어지는 카드라 동시에 만들 일이 없습니다. 001부터 순서대로 붙입니다. (H는 8/25 종합 회의, P는 Gate 1 — 같은 8/25 회의, M은 Gate 2에서만 생성)

### 팀원3 배치에 대한 설명 *(권장안 — 본인 의사 확인 필요)*

팀원3에게 리서치 운영을 제안하는 이유는 세 가지입니다.

1. **리크루팅이 이 프로젝트의 최대 병목입니다.** 설계와 분석은 AI로 압축되지만, 사람을 모으는 시간은 압축되지 않습니다. 프로젝트 성패가 여기 달려 있어서, 다른 작업에 시달리지 않는 사람이 전담해야 합니다.
2. **사람을 다루는 역량이 핵심인 일입니다.** 응답자를 설득하고, 설문 진행 상황을 챙기고, 테스트에서 참가자를 편하게 만드는 일에는 개발 지식이 필요 없습니다.
3. **저장소를 만질 일이 가장 적은 역할입니다.** 개발 도구에 익숙하지 않을 때 리스크가 가장 낮습니다.

즉 이 배치는 "개발을 못 하니까 남는 일"이 아니라, **가장 중요한 병목을 가장 여유 있는 사람이 맡는 배치**입니다.

> 폴더 자체는 남아 있어서 어디에 둘지는 알 수 있습니다.

### 카드 한 장 쓰는 법

카드는 그냥 텍스트 파일입니다. 맨 위에 정해진 항목 몇 개를 적고, 아래에 내용을 씁니다.

**외부 자료 카드 예시** (`01_evidence/desk/E-401.md`)

```markdown
---
id: E-401
type: desk
author: 팀원3
date: 2026-08-12
summary: 20대의 61%가 본인 보험 보장 내용을 모른다고 답함
source_org: 보험연구원
published: 2025-11-20
url: https://www.kiri.or.kr/report/xxxx
local_file: sources/보험연구원_2025_MZ세대보험인식.pdf
page: 12-14
grade: B
---

## 사실 (자료에 적힌 그대로)
20대 응답자의 61%가 "본인이 가입한 보험의 보장 내용을 정확히 모른다"고 답함.
30대는 44%, 40대는 29%.

## 내 해석 (내 생각)
연령이 낮을수록 본인 보험을 파악하지 못하는 경향.
SuperSOL이 20대에게 보장 내용을 요약해주지 않으면 이 격차가 그대로 남을 가능성.
```

**꼭 지킬 규칙 두 가지**

1. **"사실"과 "내 해석"을 반드시 나눠서 쓰세요.** 이게 이 프로젝트의 신뢰도를 지키는 가장 중요한 습관입니다. 자료에 적힌 것과 내가 생각한 것이 섞이면, 나중에 발표에서 "그건 근거가 뭐예요?"라는 질문에 답할 수 없습니다.
2. **카드는 짧게, 여러 장으로.** 한 파일에 다 몰아쓰지 마세요. 근거 하나 = 카드 한 장입니다.
3. **맨 위 항목에 `summary`(한 줄 요약)를 빠뜨리지 마세요.** 모든 카드에 필요합니다. 나중에 카드가 수백 장이 됐을 때 이 한 줄만 모아 보게 됩니다.

**화면 분석 카드는 이렇게 나눕니다**

```markdown
## 화면에서 확인되는 사실
보험 Tab 첫 화면에 카드가 6개 있고, 그중 3개는 상품 광고이며
내 보험 현황은 스크롤을 2번 내려야 나온다.

## UX 관점 해석 (아직 문제 아님)
사용자가 자기 보험 상태를 먼저 보고 싶어 한다면, 현재 배치는
우선순위가 어긋나 있을 가능성이 있다.
```

**AI가 만든 카드도 마찬가지입니다.** AI가 "이건 문제입니다"라고 단정하면 그 표현을 "~할 가능성이 있다"로 고쳐주세요. 아직 사용자에게 안 물어봤으니까요.

### 가설 카드 예시

가설 카드만 폴더가 두 군데입니다.

| 어디 | 무엇 | 누가 만드나 |
|---|---|---|
| `02_hypothesis/draft/` | AI가 만든 **초안** | AI (8/13~, 회의 전까지) |
| `02_hypothesis/` | 팀이 **확정한** 가설 | 8/25 종합 회의 |

**왜 나눴나:** AI가 카드를 전부 읽고 가설 후보를 10개쯤 뽑아줍니다. 그중 무엇이 진짜
가설인지는 팀이 회의에서 정합니다. 둘을 같은 폴더에 두면 나중에 "이건 AI가 뽑은 거야,
우리가 정한 거야?"를 구분할 수 없습니다. 근거 카드(O·E·S·C)는 사람이 직접 쓰는
것이라 이런 구분이 필요 없습니다.

아래는 확정된 카드 예시입니다 (`02_hypothesis/H-003.md`).

```markdown
---
id: H-003
author: 팀장
date: 2026-08-17
summary: 보험 Tab 정보 우선순위가 불명확할 가능성
status: hypothesis        ← 아직 검증 안 됨
evidence: [O-002, S-107, E-401, C-204]   ← 근거 카드 ID들
source_types: [team, screen, desk, competitor]   ← 최소 2종류 필수
validated_by: null
---

## 문제 가설
SuperSOL 보험 Tab의 정보 우선순위가 명확하지 않아,
사용자가 자신의 보험 상태를 빠르게 파악하기 어려울 가능성이 있다.
```

`evidence`에 적은 ID들 덕분에, 나중에 "이 개선안 왜 만들었어요?" → 개선안 → 진짜 문제 → 가설 → **원본 자료의 URL과 페이지**까지 한 번에 되짚을 수 있습니다.

**가설 하나에는 서로 다른 종류의 근거가 최소 2개 있어야 합니다.** 팀 관찰만 4개 있는 건 안 됩니다. 우리끼리 그렇게 느낀 것일 수 있으니까요.

## 7. Claude Code와 Git 사용법

> 📄 **처음 시작하는 분은 `00_project/START_HERE.md`부터 보세요.**
> 첫날 할 일만 담은 짧은 문서입니다. 자세한 사용법은 `HOWTO.md`에 있습니다.

### 개발 지식 없이도 되는 부분

우리는 **Git**이라는 도구로 자료를 공유합니다. 4명이 각자 작업한 걸 자동으로 합쳐주고, 누가 언제 뭘 했는지 기록이 남는 도구입니다.

**하지만 Git 명령어를 배울 필요는 없습니다.** Claude Code에 다음 두 줄만 치면 됩니다.

| 언제 | 뭘 치나 | 무슨 일이 일어나나 |
|---|---|---|
| **작업 시작할 때** | `/start` | 팀원들이 올린 최신 자료를 받아오고, 지난번 이후 뭐가 바뀌었는지 한국어로 요약해줍니다 |
| **작업 끝낼 때** | `/save` | 내가 만든 파일을 팀 저장소에 올립니다. 문제가 생기면 뭐가 문제인지 한국어로 설명해줍니다 |

**매일 쓰는 건 이 두 개가 전부입니다.**

### 팀원3만, 정해진 때에만 쓰는 것 하나

설문 응답이나 테스트 기록에는 이름·연락처가 들어 있습니다. 그대로 올리면 안 되고,
이름을 지운 사본만 올려야 합니다. 그 작업을 대신 해주는 것이 `/anonymize`입니다.

| 언제 | 뭘 치나 | 무슨 일이 일어나나 |
|---|---|---|
| 설문 마감 후 (8/19)<br>테스트 후 (9/13경) | `/anonymize` | 원본을 읽고, **무엇을 지울지 먼저 보여준 뒤** 확인을 받고, 이름을 `P01, P02...`로 바꾼 사본을 만들어줍니다 |

지우기 전에 반드시 목록을 보여줍니다. 원본은 저장소에 올라가지 않아서, 잘못 지우면
나중에 대조할 방법이 없기 때문입니다. **목록을 눈으로 확인하고 답해주세요.**

### 이런 것도 있습니다 — 지금은 몰라도 됩니다

아래 넷은 **팀장이 정해진 회의에서만** 씁니다. 외울 필요 없고, 이런 게 있다는 것만
알아두면 됩니다.

| 뭘 치나 | 누가 언제 |
|---|---|
| `/gate1` | 8/25 종합 회의. **진짜 문제(P) 카드는 여기서만 만들어집니다** |
| `/gate2` | 9/16 Gate 2 회의. 개선 효과(M) 카드는 여기서만 만들어집니다 |
| `/audit` | 팀장이 주 1회. 근거가 끊긴 곳을 기계적으로 찾습니다 |
| `/redteam` | 설문·발표자료를 트집 잡아 검사합니다 (설문 감사는 8/13·8/14 완료) |

**P 카드를 손으로 만들지 마세요.** Gate 1을 거치지 않은 카드는 검사에서 걸립니다.
1절 원칙("확인된 것만 진짜 문제")을 지키는 장치입니다.

### 지켜야 할 것

- ✅ 작업 시작 전에 **반드시** `/start` — 안 하면 남이 고친 걸 덮어쓸 수 있습니다
- ✅ 그날 작업 끝나면 `/save` — 미루면 나중에 꼬입니다
- ✅ 내 번호 대역의 파일만 만들고 고치기 (5절 참고)
- ❌ 남의 번호 카드를 고치지 않기 (필요하면 그 사람에게 말하기)
- ❌ 잘 모르는 Git 명령어를 직접 치지 않기 — `/start`, `/save`로 안 되면 팀장에게 물어보기

> 안전장치가 걸려 있습니다. 되돌릴 수 없는 위험한 명령어(강제 덮어쓰기 등)는 실행되지 않도록 막아뒀으니, 실수로 프로젝트를 날릴 걱정은 하지 않아도 됩니다.

### 문제가 생기면

`/save`가 실패하면 화면에 뜨는 메시지를 그대로 팀 단톡에 붙여넣으세요. 대부분 30초 안에 해결됩니다. 혼자 해결하려고 이것저것 시도하는 게 오히려 더 위험합니다.

| **감사 도우미** | **다른 도우미가 만든 걸 트집 잡기** | 지적 리포트 | ✅ 있음 |
| 설문설계 도우미 | 가설을 설문 문항으로 바꾸기 | 설문 초안 | ⬜ 설문 설계 전까지 |
| 분석 도우미 | 설문·테스트 결과 계산과 정리 | 분석 리포트 | ⬜ 설문 회수 전까지 |

카드를 쓰는 일(O 카드 포함)은 도우미 없이도 됩니다. **8/5부터 바로 쓸 수 있습니다.**

**감사 도우미를 따로 둔 이유:** 자기가 만든 설문을 자기가 검수하면 통과시킵니다. "우리가 원하는 답을 유도하지 않는다"는 원칙은 만드는 쪽과 검사하는 쪽이 분리돼야 지켜집니다. 설문 초안이 나오면 반드시 감사 도우미에게 한 번 걸러야 합니다.

### 사람이 반드시 하는 것

| 사람이 함 | AI가 함 |
|---|---|
| 무엇이 진짜 문제인지 판정 | 자료 모으고 정리 |
| 어떤 개선안을 선택할지 | 개선안 후보 여러 개 제시 |
| 사용자 조사 진행 | 조사 설계 초안 |
| 최종 디자인 결정 | UX 패턴 조사 |
| 발표에서 뭘 말할지 | 자료 요약 |

### AI가 절대 하면 안 되는 것

1. AI가 찾은 문제를 "사용자 Pain Point"라고 단정하기
2. 근거 없는 내용을 사실처럼 쓰기
3. 출처 없이 통계나 수치 쓰기
4. 경쟁사가 뭘 제공한다고 확인 없이 주장하기
5. **사용자 조사 결과와 AI 예상이 다를 때 AI 쪽을 따르기** — 무조건 사용자 조사가 이깁니다

### 의사결정 기록

AI가 여러 안을 제시하고 팀이 하나를 고를 때마다 `_meta/decision_log.md`에 한 줄씩 남깁니다.

```
2026-09-03 | SOL-002 | AI가 3안 제시(요약카드 / 챗봇 / 진단플로우)
           → 2안 제외(개발 범위 초과), 1안 선택
           → 이유: P-001의 "한눈에 파악" 요구에 가장 직접적으로 대응
```

이 파일이 "AI가 다 한 프로젝트 아니냐"는 질문에 대한 우리의 답입니다.

### 일정이 밀리면 자를 순서

급할 때 정하면 잘못된 걸 버립니다. **미리 순서를 정해둡니다.**

1. 경쟁 앱 3개 → 2개
2. 데스크 리서치 주제 9개 → 5개 (연령별 인식·행태·니즈 중심)
3. 진짜 문제 4개 → 3개, 프로토타입 화면 6개 → 4개
4. 사용자 테스트 8명 → 5명
5. 테스트 과제 3개 → 2개

### 절대 자르면 안 되는 5가지

이 중 하나만 빠져도 "근거 중심 UX 프로젝트"라는 우리 주장 자체가 성립하지 않습니다.

1. **설문 배포와 회수 (8/15 오후 ~ 8/19)**
2. **Gate 1 (8/25 종합 회의)**
3. **테스트 순서 절반씩 바꾸기**
4. **"우리가 틀렸던 것" 슬라이드** (아니었던 가설 공개)
5. **한계점 슬라이드**

### 4번, 5번을 강조하는 이유

발표에서 가장 신뢰를 얻는 슬라이드는 "우리가 다 맞혔습니다"가 아니라 **"우리는 이것도 문제라고 생각했는데, 사용자에게 물어보니 아니었습니다"**입니다.

이게 우리 프로젝트의 핵심 원칙("우리 생각 ≠ 사용자의 불편")을 증명하는 **유일한 증거**입니다. 이 슬라이드가 없으면, 우리가 정말 검증을 했는지 심사자가 확인할 방법이 없습니다.

그래서 **아니었던 가설은 절대 지우지 않습니다.** `02_hypothesis/` 폴더에 `status: rejected`로 남겨둡니다.
